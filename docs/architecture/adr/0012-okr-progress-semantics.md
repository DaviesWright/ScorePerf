# ADR-0012: OKR key-result progress takes `start_value` into account; no upper cap per key result

| | |
|---|---|
| Status | **Accepted in principle. Formula details and handling of existing records are PROPOSED and await confirmation.** |
| Date | 2026-11-03 |
| Approver | paa.barnes (decision); details pending |
| Changes protected behaviour | `BUILD.md` §1.1(1), §2.2 and §22: OKR behaviour changes only with approval |
| Relates to | `pms/tests/test_progress_calculation.py`, `pms/tests/test_okr_api_contract.py` |

## Context

Today `EmployeeKeyResult.update_kr_progress` computes `int(current / target * 100)`. It ignores `start_value`, leaves progress unchanged when the target is 0, and does not cap a key result at 100 (the objective average caps each key result at 100). This is pinned by tests.

Because `start_value` is ignored, a key result that starts at 20 and targets 10 (for example "reduce complaints") reports misleading progress, and one that starts at 40 and targets 100 over-reports.

Two related facts found while writing the contract tests and sample-data generator:

- `EmployeeKeyResult.clean()` rejects `start_value` greater than `target_value`, so **decreasing key results cannot be created in the UI today**. Only the API can create them (and then progress is wrong). With the proposed formula, decreasing key results become meaningful, so that validation rule must be revisited in the same ticket.
- The `unique_together` on key result and employee objective is declared in a lowercase `class meta:`, so **Django never applies it**. Duplicates can exist; `clean()` checks for them only in forms. Fixing it needs a data check for existing duplicates first (separate ticket).

## Decision (owner, 2026-11-03)

1. `start_value` **will** affect key-result progress.
2. Key-result progress **stays uncapped** above 100 (current behaviour retained). The objective average still caps each key result at 100.

## Proposed details (need confirmation)

- Formula: `progress = (current - start) / (target - start) * 100`, truncated to an integer as today. It works for increasing and decreasing key results.
- With `start_value = 0` (the default) this equals today's formula, so existing records with a start of 0 do not change.
- If `target == start`: leave progress unchanged (mirrors today's zero-target rule), no division.
- If the result is below 0 (current worse than the start): **floored at 0. DECIDED 2026-11-03 (paa.barnes).** There is no cap above 100.
- Existing records with a non-zero `start_value` would change when recalculated. **Recalculate stored progress, or apply only to new updates?** Per `BUILD.md` §6.3 and §22, do not change stored results silently. Recommended: a reported, reversible backfill that records old and new values, run only after approval.

## Measured impact (synthetic sample data, 2026-11-03)

Produced with `python manage.py report_okr_progress_impact` on `SampleOKR.sqlite3`, which holds **synthetic** data generated by `generate_sample_okr_data`. These figures show the shape of the change, **not** your real impact. Run the same command on a protected production copy before deciding.

| Measure | Result |
|---|---|
| Employee key results examined | 561 |
| Would change under the new formula | **114 (20.3%)** |
| of which: non-zero start value | 96 |
| of which: decreasing key result (start above target) | 18 |
| Undefined under the new formula (target equals start, left unchanged) | 32 |
| Size of change | max 80 points, mean 30.7 points |
| Employee objectives whose progress would change | **81 of 245** |
| Stored progress already differing from today's formula | 8 (stale rows) |

The sample deliberately makes about 18% of key results have a non-zero start, so the 20% figure is driven by that assumption. Real data will differ. The size of the changes (mean about 31 points) is why recalculating stored progress is an owner decision, not a silent migration.

## Implementation rules

- A separate, small ticket. It changes one method plus the tests, and the characterisation tests (`test_start_value_does_not_affect_progress`) are updated in the same commit, with the reason in the commit message.
- API contract tests must still pass unchanged except for values that depend on the formula.
- Needs production-like data to measure how many rows change (see sample-data work).

## Alternatives considered

- Keep current behaviour: rejected by the owner.
- Add a per-key-result "progress mode" setting: more flexible but adds configuration and complexity. Not chosen.
